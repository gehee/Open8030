# Board profiles

These files configure hardware; the AP/DEV protocol role is selected separately.
Use descriptive product names, such as `ascent-vrx.c`. Add a board-ID or revision
suffix only when needed to distinguish incompatible configurations.
Keep hardware identifiers in the profile documentation even when omitted from
the filename. A shared board number
does not establish compatibility between products, transports or revisions.

| Profile | Hardware / scope |
|---|---|
| `ascent-vrx.c` | Regular Ascent VRX, SDIO DEV; matched v0.2.0 bench profile |
| `ascent-lite.c` | Upstream Lite profile, SDIO AP |
| `ascent-lite-plus.c` | Upstream Lite Plus profile, SDIO AP |
| `betafpv-p1-air.c` | BETAFPV P1 Air Unit, stock 1.0.44, SDIO AP; profile only, transport integration pending |
| `ascent-vrx-pro.c` | Upstream VRX Pro profile, USB DEV |
| `steadyview-vrx.c` | Upstream SteadyView receiver profile |
| `board-profile.c` | Upstream legacy default, labelled VRX Pro; not an alias for the regular VRX |

P1 uses its own profile recovered from the fpvOS P1 integration, not a Lite or
Lite Plus alias. Inclusion of a profile does not establish hardware validation
of the current firmware or provide a loading procedure for that board.

## Building the board configurations

After installing the dependencies described in the root README, use the existing
`image` command to build current source without the historical release hash gate:

```sh
./open8030 image --profile profiles/ascent-vrx.c \
  --output .local/open8030-ascent-vrx-rx.img \
  --build-dir .local/build-ascent-vrx-rx
./open8030 image --profile profiles/ascent-lite.c \
  --cflags='-DAR_ROLE_AP -DAR_FACTORY_OPTIONAL' \
  --output .local/open8030-ascent-lite-tx.img \
  --build-dir .local/build-ascent-lite-tx
```

For a new checkout, `./open8030 qemu --prepare` installs the pinned dependencies
and exercises the QEMU protocol target without a hardware profile. The `build`
and `run` commands still enforce the recorded release baseline; do not replace
its hashes merely to make newly compiled firmware pass as hardware-validated.
The commands above compile and package images, not load devices. Board-specific
loader JSON is supplied separately by the host at runtime.

## Provenance and comparison

The regular `ascent-vrx.c` profile preserves the data used in the October 22,
2026 v0.2.0 dual-radio bench test; only its source comments changed for publication.
Current firmware includes subsequent upstream changes and has not inherited that
hardware-validation result simply by using this profile.

- Matched stock container SHA-256:
  `dc58247910af564376350404383c5c411cbec21663873fba24e70c61a3584e3c`.
- Original generated VRX profile SHA-256:
  `1bc673f086b67f2a742233619d655d92aca6816932a57e2b674cbdbd4f6f12c5`.

The regular VRX profile has 10 pin records and 19 flash-part records. Its register
defaults differ from upstream `board-profile.c`, which has one flash-part record.

For Lite VTX, use gehee’s `ascent-lite.c` unchanged. Our earlier bench profile
had the same 26 pin records and FCH keys, but different register defaults,
automatic I/O-domain selection and a flash table. The selected gehee profile
explicitly selects domain mask 4 and uses SFDP. We do not maintain that older
Lite configuration as a second public board target.

The tables originate from stock firmware; their publication does not establish
an upstream license grant or make them independently authored MIT code. See
[third-party notes](../THIRD_PARTY.md). Original firmware binaries and private
research artifacts are not needed to compile the included C sources.

For a new target, record its board/revision, transport, source provenance, pin and
power assumptions, and hardware results. Reuse data only after comparing it;
different interfaces or RF circuitry may require driver changes as well.

## BETAFPV P1 Air Unit

`betafpv-p1-air.c` is the AP profile generated by fpvOS's
`br-external/package/p1-air-vendor/generate-radio-profile.py` for stock
`P1_SKY_v1.0.44_20260122_09de6e7`. It contains 704 register-default records,
23 pin/pad records, 25 FCH keys, 19 flash-part descriptors and I/O-domain mask 2.
It was regenerated and compared byte-for-byte with fpvOS's existing generated
`p1-air.c`; only the publication comment differs.

Provenance:

- Stock `bb_demo_air_d.img` SHA-256:
  `fa80c8d72af34c8b25830b34124b0b08e0073b2d6d1dc7eb530cec42eaf4f12f`.
- Runtime segment at offset 17,920, length 266,432, SHA-256:
  `fcfdb46210f990b5b62c31c5d8c6ddcce436a62b43ec3d202b1af3a7eaf48e9c`.
- AP defaults SHA-256:
  `9987cdba49455ce3cfd4572ca5f3e3767ea4f653e709d0b8daf2c4333a16369d`.
- Pin records SHA-256:
  `518584c82b390844692baa4c44261b6612dcb8e569143a196e60b05b51c9e449`.

The user reports a working P1 air-unit build in fpvOS. Older prototype records
cover radio association, camera initialization and command transport, but do not
represent the validation status of that newer integration. This change imports
the profile data, not the complete fpvOS firmware patch set or host application.
The profile is specific to the recorded 1.0.44 evidence; compatibility with P1 v2
firmware or other P1 hardware revisions is not established here.

The fpvOS build selects AP, pins-before-factory and optional factory calibration,
plus its `0001-stock-p1-sdio-transport.patch`. That patch adds stock P1's
`00 DD length_le16` SDIO block trailers and explicit clearing/setting of I/O-domain
bits (`AR_SDIO_P1_TRAILER` and `AR_EXPLICIT_IO_DOMAINS`). Those two options are not
implemented here: passing their names as compiler flags alone does not enable
them. Current-source compilation with this profile is an offline check, not a
reproduction of the working fpvOS P1 build. Its host integration and hardware
validation need to be assessed separately when porting the remaining changes.
No P1 loader is provided by this repository.
